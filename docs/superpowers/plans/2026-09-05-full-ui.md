# Local File Converter - Plan 3: The Real UI

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the 107-line proof-of-slice renderer with the interface the design spec describes, and add the three engine capabilities it depends on.

**Architecture:** Unchanged. The renderer stays sandboxed with no `@types/node`; everything it needs arrives through the preload bridge. Three engine additions come first because the UI cannot be built without them.

**Tech Stack:** Electron, TypeScript, React, Tailwind, vitest. Node 24, npm. macOS arm64.

**Branch:** `feat/ui`, stacked on `feat/converters-ffmpeg-poppler` (PR #2).

---

## Why the first three tasks are engine work

The spec asks for per-file progress rows, a picker grouped by medium, and cancellation. An audit of the current engine surface found none of them are reachable from the renderer:

- **Progress is emitted but never forwarded.** `JobRunner` extends `EventEmitter` and emits `progress` events, but `src/shared/ipc.ts` has only four request/response channels and no event stream. The renderer literally cannot observe a running conversion.
- **Cancellation does not exist.** `job.ts` has a timeout, but nothing lets a user stop a batch. A user who drops a 2GB video has no way out.
- **Format categories are flattened away.** `registry.outputsFor()` returns a flat sorted array. Grouping by medium needs a category per format.

That last one carries the same lesson as Plan 2's `MEDIA_INPUTS`: **upstream's category keys cannot be used.** ImageMagick files every format it knows - including `mp4` - under `images`, and ffmpeg files everything under `muxer`. A picker grouped on those keys would put `mp4` under Images and every video format under a heading called "muxer". The medium classification has to be ours, and it has to be tested against the real tables so a future converter cannot silently leave formats unclassified.

## A note on how Tasks 5 to 8 are specified

Tasks 1 to 4 give exact code, because they are engine and build changes where the precise shape matters and a wrong guess is expensive.

Tasks 5 to 8 are React components, and are specified by BEHAVIOUR and acceptance criteria instead. That is deliberate: inlining four components would triple this plan's length, and for UI the observable behaviour is what needs pinning, not the markup. Each of those tasks still names its files, its required behaviours, and what must be tested.

Where a UI task contains real logic rather than presentation - the picker's multi-file intersection in Task 6 - the plan calls for a unit test specifically, because that part is pure, easy to get wrong, and impossible to eyeball.

## Deferred from this plan

Two spec items are deliberately NOT here, to keep the plan executable:

- **Per-converter options** (ffmpeg quality/codec, image resize). Needs a schema per converter and a generated form; it is a plan of its own.
- **A configurable output folder.** Output continues to default to the input file's directory, which is the common case.

Both are recorded in Open Items.

 *
 * This classification is OURS, not upstream's. ConvertX's converters group
 * their format tables by whatever suited the tool: ImageMagick files every
 * format it knows - including mp4 - under "images", and ffmpeg files
 * everything under "muxer". Grouping the picker on those keys would show mp4
 * under Images and every video format under a heading called "muxer".

    groupedOutputsFor(input) {
      const outputs = this.outputsFor(input);
      const groups = new Map<Medium, string[]>();
      for (const format of outputs) {
        const medium = mediumOf(format);
        const bucket = groups.get(medium);
        if (bucket) bucket.push(format);
        else groups.set(medium, [format]);
      }
      return MEDIA_GROUP_ORDER.filter((medium) => groups.has(medium)).map((medium) => ({
        medium,
        formats: groups.get(medium)!,
      }));
    },

### Task 1b: Do not offer formats nobody would pick

Task 1's real-table check found that **76% of reachable formats land in "Other"** - 260 of 339 for a png input. Inspecting them shows the classification is not the problem. The bucket is almost entirely:

- **ImageMagick pseudo-formats that are not files at all**: `null`, `clipboard`, `histogram`, `info`, `mask`, `matte`, `inline`, `data`, `thumbnail`, `sparse`.
- **Codec-only ffmpeg muxer names**: `264`, `265`, `266`, `h261`, `h263`, `hevc`, `vc1`, `vc2`, `obu`, `adts`.
- **Variant spellings of formats already classified**: `png8`/`png24`/`png32`/`png00` beside `png`, `bmp2`/`bmp3` beside `bmp`, `eps2`/`eps3`/`epsf`/`epsi` beside `eps`, `gif87` beside `gif`.

So the fix is not to classify harder. It is to stop offering them. A picker listing 260 unlabeled entries is worse than one listing 80 useful ones, and `null` or `histogram` appearing as a conversion target is simply a bug from the user's point of view.

Two changes: add the one genuinely missing medium, and let the UI collapse the remainder.

In `src/main/engine/media.ts`:

```ts
/**
 * Formats that are reachable but should never appear in the picker.
 *
 * ImageMagick's format table includes pseudo-formats that are not files at all
 * (`null`, `clipboard`, `histogram`), ffmpeg's includes bare codec names that
 * are not containers (`264`, `hevc`), and both include variant spellings of
 * formats already offered under their canonical name (`png8`, `bmp2`, `eps2`).
 *
 * Offering "convert to null" is a bug from the user's point of view. Three
 * quarters of the raw reachable set is this kind of noise.
 */
const NOT_OFFERABLE = new Set([
  "null", "clipboard", "histogram", "info", "mask", "matte", "inline", "data",
  "sparse", "thumbnail", "map", "pal", "icon", "mono", "gray", "graya",
  "cmyk", "cmyka", "rgb", "rgba", "rgbo", "bgr", "bgra", "bgro", "ycbcr",
  "ycbcra", "yuv", "uyvy", "bayer", "bayera", "vid", "strimg", "ashlar",
  "264", "265", "266", "h261", "h263", "hevc", "vc1", "vc2", "obu", "adts",
  "m2v", "a64", "ac4", "302",
]);

/** Variant spellings whose canonical form is already offered. */
const VARIANT_PATTERN =
  /^(png(00|8|24|32|48|64)|bmp[23]|eps[23]|epsf|epsi|ept[23]?|gif87|ps[23]|tiff64|jpe|pjpeg|jpc|jp[mt]|pcds|dcx)$/;

export function isOfferable(format: string): boolean {
  const key = format.toLowerCase();
  if (NOT_OFFERABLE.has(key)) return false;
  if (VARIANT_PATTERN.test(key)) return false;
  return true;
}
```

Filter `groupedOutputsFor`'s results through `isOfferable` in `registry.ts`. Leave `outputsFor` unfiltered - it is the honest full set, and the routing tests depend on it.

import type { BrowserWindow } from "electron";
import type { JobRunner, ProgressEvent } from "./engine/job";
import { IPC } from "../shared/ipc";

/**
 * Forwards the runner's progress events to the renderer.
 *
 * The window can be closed mid-batch, and sending to destroyed webContents
 * throws - which inside an EventEmitter handler would surface as an unhandled
 * error and take down the conversion. Guard every send.
 */

## Definition of Done

- Formats are classified by our own medium map, tested against the real converter tables.
- Progress streams to the renderer and survives a window closed mid-batch.
- A running batch can be cancelled, in-flight children are killed, and a later run is unaffected.
- Tailwind genuinely processes - verified by inspecting the built CSS, not assumed.
- Multiple files convert in one batch with per-file progress and per-file failure.
- The picker groups, searches, and explains why a format is unavailable.
- The Formats panel names the Office gap explicitly.
- `npm test` green, `tsc -b` exit 0, `npm run build` succeeds.
- The manual checklist in Task 9 has been completed by a human.

## Open Items

**`openPath` and `reveal` accept any string from the renderer.** Neither validates that the target is a path the app itself produced. The current UI only ever passes an `outputPath` from a `run()` result, so there is no live exploit, and the app is sandboxed and offline. But the preload surface is more permissive than the UI needs: any future renderer-side bug could open or reveal an arbitrary file. Fix by having the main process keep the set of paths the runner actually wrote and rejecting anything else. Decide in Plan 4, before the app is distributed to anyone else.


**Per-converter options are deferred.** ffmpeg quality and codec, image resize and quality. Needs a per-converter option schema and a generated form.

**A configurable output folder is deferred.** Output stays in the input file's directory.

**Poppler renders page 1 only.** A 40-page PDF silently yields one image named `doc.png`. The UI should surface the page count, or the converter should emit one file per page. Carried from Plan 2.

**`.wmv` has no ffmpeg fallback and `.ts` cannot be converted at all.** Inherited from upstream's tables. Carried from Plan 2.
